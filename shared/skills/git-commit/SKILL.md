# 커밋 분해 (최대 분해 원칙)

> `shared/git-flow.md`가 흐름(최신 dev 기준 작업 브랜치·dev 대상 PR)의 진실 소스다.
> 이 스킬은 **"한 커밋에 무엇을 담을 것인가"** 만 다룬다.

## 0. 왜 잘게 쪼개나

팀이 **커밋 수를 활동 지표로 보고 있다**(2026-08-18 사용자 확인). **지표가 바뀌면 이 절을 재검토한다** — 근거가 사라졌는데 규칙만 관성으로 남지 않게. 그래서 이 프로젝트의 기본값은
"논리 단위로 적당히"가 아니라 **최대 분해**다 — 의미가 서는 가장 작은 조각마다 커밋한다.

부수 효과도 실제로 있다: 리뷰가 조각 단위로 읽히고, 되돌릴 때 한 조각만 되돌린다.

## 1. 분해 기준 — "의미가 서는 가장 작은 조각"

한 커밋 = **한 가지 사실의 추가/변경**. 파일 경계보다 더 잘게 간다.

| 축 | 커밋 하나가 되는 예 |
|---|---|
| 타입·스키마 | `ItemResponse` 타입 정의 / `itemSchema` zod 정의 / 쿼리 파라미터 타입 정의 |
| 함수 | `getItems()` 골격 추가 / `getItems()` 에러 처리 추가 / `getItems()` 캐싱 태그 명시 |
| 라우트 | `GET /api/items` 핸들러 추가 / 해당 핸들러 입력 검증 추가 |
| 훅 | `useGetItemsAPI` 추가 / queryKey 팩토리 추가 |
| UI | 컴포넌트 골격 / 상태 3종(로딩·에러·빈) 각각 / a11y 속성 추가 |
| 토큰·스타일 | 토큰 그룹 하나 / `/playground` 스토리 하나 |
| 설정·문서 | 의존성 추가 / env 예시 추가 / 문서 절 하나 |

**목표 감각**: 보통의 기능 하나가 커밋 **5~15개**로 나온다. 3개면 덜 쪼갠 것이다.

## 2. 쪼개지 않는 경우 (예외)

무리하게 쪼개서 오히려 히스토리가 거짓말이 되는 경우가 있다. 아래는 한 커밋에 둔다:

- **이름 변경**: 정의와 모든 호출부는 **같은 커밋**. 나누면 중간 커밋이 존재하지 않는 심볼을 부른다.
- **파일 이동/삭제**: 이동과 참조 갱신은 함께.
- **자동 생성물**: `pnpm gen:codex` 결과(`.codex/agents/*.toml`)는 원본(`.claude/agents/*.md`) 커밋과 **같은 커밋**(CLAUDE.md 어댑터 규칙).
- **lockfile**: 의존성 추가 커밋에 `pnpm-lock.yaml` 포함.
- **한 줄 오타 수정 여러 개**: 같은 성격이면 하나로 묶어도 된다(커밋 수를 위해 오타를 3개 커밋으로 나누지 않는다 — 이건 지표 조작이지 분해가 아니다).

## 3. 중간 커밋이 빌드를 깨도 되는가

**된다 — 단 조건부.**

- CI(`build-check`)는 **푸시 단위**로 돈다. 즉 **푸시하는 시점의 HEAD가 통과하면 된다.**
- 그래서 함수 골격만 있는 중간 커밋이 타입 에러를 내도 괜찮다.
- **단 마지막 커밋을 만든 뒤 `pnpm build` 1회**(conventions #6) 통과를 확인하고 푸시한다.
- ⚠️ 트레이드오프를 알고 쓴다: 중간 커밋으로 `git bisect`·단일 커밋 revert가 항상 되지는 않는다.
  되돌릴 땐 **조각 묶음(range)** 을 되돌린다. 되돌리기 안전성이 중요한 변경(인증·결제 등 위험 경로)은
  **각 커밋이 빌드 통과하도록** 순서를 잡는다(타입 → 함수 → 사용처).

## 4. 순서 규칙

의존성이 낮은 것부터 쌓아 올린다. 그래야 중간 커밋이 최대한 성립한다.

```
타입/스키마  →  순수 유틸  →  서버 fetch 함수  →  BFF 라우트  →  클라 훅  →  화면 연결  →  문서 갱신
```

## 5. 메시지 형식

`git-flow.md`의 형식을 그대로 쓴다: `type(scope): 한국어 설명`
(`feat|fix|design|refactor|chore|style|docs|test`)

- scope는 **기능·도메인 이름**으로 (`items`, `auth`, `stores`) — 파일명이 아니다.
- 설명은 **무엇을 했는지 한 가지**만. "및", "그리고"가 들어가면 커밋을 덜 쪼갠 신호다.
- 조각 커밋이라도 메시지는 완결된 문장으로. `wip`·`fix2`·`.` 금지.

```
feat(items): ItemResponse 타입 정의
feat(items): items 응답 zod 스키마 추가
feat(items): getItems 서버 fetch 함수 골격 추가
feat(items): getItems 캐싱 태그(items) 명시
feat(items): GET /api/items BFF 핸들러 추가
feat(items): 쿼리 파라미터 검증 추가
feat(items): useGetItemsAPI 훅 추가
```

## 6. 스테이징 절차 (한 파일 안에서 쪼갤 때)

파일 단위 `git add`로는 함수 단위 분해가 안 된다. **hunk 단위로 스테이징**한다.

```bash
git status
git diff                      # 전체 파악
git add -p <파일>             # hunk 선택 (y/n/s로 더 쪼개기)
git diff --cached             # 스테이징된 것만 재확인 — 커밋 전 필수
git commit -m "feat(items): ItemResponse 타입 정의"
```

- `git add -p`가 인터랙티브라 막히는 환경이면, 순서를 바꿔서 **작업할 때부터 조각 단위로 저장하고 바로 커밋**한다(쓰기 → 커밋 → 다음 조각 쓰기). 이 방식이 더 안전하고 빠르다.
- **`git add .` 금지** — 의도하지 않은 파일이 딸려 들어간다.
- 커밋 전 `git diff --cached`로 **이 커밋에 담긴 것이 메시지 그대로인지** 확인한다.

## 7. 커밋에 들어가면 안 되는 것

- 작업 보조 산출물(플랜·설계 MD, 미리보기 HTML) — conventions #12
- `.env.local` 등 시크릿, `.next/`·`node_modules/` 등 빌드 산출물
- 요청에 없는 리팩토링 (conventions #4) — 커밋 수를 늘리려고 무관한 정리를 끼워 넣지 않는다

## 8. 푸시

분해는 커밋 단위이지 푸시 단위가 아니다. **여러 커밋을 모아 한 번에 푸시한다.**

```
푸시 전 code-reviewer 1회 → 최종 검증 → git fetch origin dev → 최신 dev와 정렬 → 작업 브랜치 push → dev 대상 PR
```

충돌은 **자동 해결 금지, 사용자에게** (`git-flow.md`).
